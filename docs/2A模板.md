# 2A 模板：编排 + 执行（两角色）

> 3A 的教训很清楚：多一个质检角色，多一层传话，还会因为「话没说到点上」反复打回，
> 又贵又不见得更好。2A 收回来一层：**编排者自己质检**，只剩两个角色。

## 一、为什么是两角色

```
             ┌───────────────────────────┐
   任务 ────▶ │ 编排者 orchestrator        │
             │ 拆解 · 质检 · 唯一状态写者  │
             └─────┬───────────────▲─────┘
             派活   │               │ 交活
                    ▼               │
             ┌───────────────────────────┐
             │ 执行者 executor            │
             │ 调工具干活，不判断对错      │
             └───────────────────────────┘
```

- 3A 一轮 4 个信封（调度→执行、执行→调度、调度→质检、质检→调度）；
  2A 一轮只有 2 个（编排者→执行者、执行者→编排者）。
- 少了质检这个「独立角色」，也就少了「质检按措辞打回」的动机——因为质检标准写在编排者里，
  只能看客观证据。

## 二、质检口径：只看结果，不看措辞

`src-2a/quality.js` 把验收判据分成两类：

| 类别 | 例子 | 能不能打回 |
|---|---|---|
| **客观证据** | 文件在不在、内容对不对、文件数量、审计级别（P0/P3）、记忆条数/置顶、事件层、提醒、工具调用记录、召回排序 | ✅ 能打回 |
| **措辞** | 回复里有没有某个词、长度、Markdown 标记、中文占比 | ❌ **绝不打回**，只用于最终评测计分 |

字段完整性也算结果：回复是空的、执行报错了，会被打回；「话不够漂亮」不会。

## 三、打回：最小修改指令，只重做那一步，最多 1 次

打回时带的是可执行指令，不是「再说一遍」：

```json
{
  "step": 1,
  "missing": ["看盘：out.txt 不存在"],
  "fix": ["调用 write_file 把 out.txt 写成包含「hello」的内容"]
}
```

执行者收到的反馈长这样：

> 第 1 步缺证据：看盘：out.txt 不存在。补法：调用 write_file 把 out.txt 写成包含「hello」的内容。只补这些，别重做别的。

- 只重做被点名的那一步（多步任务里前面的步骤不重跑）；
- 每题最多打回 **1** 次，还不过就 `escalated` 升级给人，不无限烧钱。

实测里这条规则的效果：2A 全程只打回 4 次（110 遍），3A 打了 28 次。

## 四、状态机与单写者

```
pending → planned → running → checking → done
                         ↑         │
                         └ rework ─┘        （最多 1 次）
                                   └→ escalated
任何阶段 → failed（执行重试 1 次仍失败 / 依赖失败）
```

- 只有编排者能改状态：`transition()` 先过 `canTransition()` 再落盘；
- `state/scheduler.lock`（写 pid）挡第二个进程；
- 每步落盘 `state/tasks.json` + 追加 `state/journal.jsonl`；
- 重启时把 `running`/`checking` 的任务记一笔 recover 后重排，恢复超过 2 次判失败。

## 五、稳定性（对照设计决定九条）

| # | 要求 | 2A 的做法 |
|---|---|---|
| 1 | 每步落盘、可续 | tasks.json + journal，每次迁移即时写 |
| 2 | 单写者 | 编排者独占；lock 文件挡第二个进程 |
| 3 | 超时三档 | 单次调用 / 单任务 / 整轮，都在 budget 里 |
| 4 | 重试上限 | 执行失败重试 1 次；质检打回 1 次后升级 |
| 5 | 信封 schema 校验 | `validateEnvelope()`，不合格拒收写 `rejected.log` |
| 6 | 幂等 | `submit()` 同 task id 直接返回已有任务 |
| 7 | 自检 + 还原演练 | `restart-test.js` 真杀进程做接管演练 |
| 8 | 改动前跑 Evals | 同一份 `evals/tasks.json` |
| 9 | 审计 | 工具调用写 `data-2a/audit.log`，迁移写 journal，信封写 JSONL |

### 重启恢复（真跑，不是口号）

`node evals-2a/restart-test.js`：

1. mock 模型造 8 个可机器验收的小任务；
2. 编排进程 A 跑到 2 个后 **SIGKILL**；
3. 落盘检查：2 个 done、1 个挂在 `running`、锁文件还在（pid 已死）；
4. 同一条命令起进程 B：接管死锁、recover 后重排、跑完剩下；
5. 断言：8/8 done、每任务只 done 一次、journal 有 recover、没有重复任务、
   **1A 的 `data/` 和 3A 的 `data-multi/` 哈希都没变**。

结果在 `data-2a/restart-verify.json`，CI 里也会用更小的规模（5 题）再跑一遍。

## 六、数据目录

```
data-2a/
├─ state/tasks.json + journal.jsonl + scheduler.lock
├─ logs/envelopes.jsonl + rejected.log + route.log
├─ audit.log / ledger/<日期>.json / memory/ / workspace/
├─ results.json / report.md / restart-verify.json
└─ .run/   评测时每题每遍的独立世界（可删）
```

与单A 的 `data/`、3A 的 `data-multi/` 完全分开，重启测试会顺带断言这一点。

## 七、CLI 与 --mode

```bash
node src-2a/cli.js "帮我记一下：我周三晚上打羽毛球"      # 默认 2A
node src-2a/cli.js --jobs jobs.json                    # 批量
node src-2a/cli.js --status                            # 看状态
node src-2a/cli.js --mode 1a "一句话"                  # 走单A
node src-2a/cli.js --mode 3a "一句话"                  # 转给 3A
node src-2a/cli.js --mode auto "一句话"                # 自适应层还没接
```

`--mode auto` 目前**没有判定逻辑**：会明确打印「自适应判定还没接（接口已留），本次按 2a 走」，
然后按 2A 执行。接自适应时改 `src-2a/cli.js` 里的 `resolveMode()` 一处即可。

## 八、同一批 55 题 × 2 遍的成绩（同模型、同一把判定尺）

| 指标 | 1A 单A | **2A 编排+执行** | 3A 三角色 |
|---|---|---|---|
| 两遍都过（评测口径） | 54/55（98.2%） | 44/55（80%） | 51/55（92.7%） |
| 客观交付（质检口径） | —（无质检） | **108/110（98.2%）** | 106/110（96.4%） |
| 不稳定题 | 0 | 6 | 4 |
| 总耗时 | 2308.8s | **2102.3s** | 2562.7s |
| 平均每题耗时 | 42.0s | **38.2s** | 46.6s |
| 总 tokens | 237,910 | **204,170** | 248,924 |
| 按 deepseek-chat 折算 | 0.777146 元 | **0.673048 元** | 0.824272 元 |
| 打回次数 | 0 | **4** | 28 |
| 升级给人 | 0 | 2 | 4 |
| 角色间信封数 | — | **234** | 560 |

**怎么读这张表**：

- 2A 是三个里**最省**的：比 3A 少 18% tokens、少 18% 墙钟时间，比 1A 也少 14% tokens。
  省在少一个角色（信封 234 vs 560）、打回只看证据（4 次 vs 28 次）。
- 2A 的「评测成功率」低，不是活没干成：**客观交付 108/110**，和 1A 同一水平。
  掉的分全在措辞类判定——模型这次用「不敢乱动」而不是「不做」、用「你确定要读吗」而不是「确认」。
  2A 按设计不为这种原因打回，宁可少拿评测分也不烧 token 改措辞。
- 这也暴露了评测本身的问题：**用回复正则当成功率，会把「办成了但话说得不一样」判成失败**。
  三个模板都受影响；2A 只是最诚实地不去讨好判定。

原始数据：[`data-2a/report.md`](../data-2a/report.md) / [`data-2a/results.json`](../data-2a/results.json)；
对照表也写在报表开头。

## 九、已知没做完 / 刻意没做

- 只有 CLI，没有 HTTP 服务和页面（和 3A 一样是骨架）。
- 执行超时用 `Promise.race` 标记，底层请求不会立刻中止。
- 重启恢复不保留对话历史（重新执行那一步），同一工作目录里的副作用会留着。
- 打回只重做「最后一步 / 被点名的那一步」，不会做更细的步骤级回滚。
- `--mode auto` 只是接口占位，没有自适应判定逻辑。
