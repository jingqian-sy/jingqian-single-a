# 动态额度策略

免费额度是「会变的」：官方会调上限、搞活动、把免费模型下线，你这边也会换 key、换机器。
写死一个「一天 50 次」的阈值，不是太早停就是撞一脸 429。所以这里不用固定阈值，用三样东西分开管：
**本地账本 + 规则刷新 + 实测探测**。三样都不需要登录你的账号。

代码在 `src/quota.js`，选路整合在 `src/router.js` 的 `quotaGate`，用例在 `evals/quota-test.js`。

## 三件事各管一段

### 1. 本地账本（`data/ledger/按天.json`）

每次真实调用后，把接口返回的 `usage` 记进当天的账本，按 provider 分组。

**能保证**：这台机器、这个进程里，今天/这个月到底用了多少 token。数字来自接口自己返回的 usage，不是估的。

**不能保证**：

- 只算本机。同一个 key 在别的机器、别的客户端、网页版后台用掉的，账本不知道；
- 只知道「接口报了多少」，不知道服务端怎么计费（缓存命中、多轮工具调用、推理 token 的算法都可能和 usage 不一致）；
- 不知道赠送额度、临时加量、按 key 分档。

所以账本算出来的 `left` 是个**偏乐观的下限估计**，不是真实余额。它负责「明显超了就别试了」，不负责「精确还剩多少」。

### 2. 规则刷新（`config.json` 的 `quotaSources` → 公开页面文本）

定期抓 `quotaSources` 里列的公开页面，用宽松正则找「每天/每月 X 万/百万 tokens」这类描述，回填到对应 provider 的 `freeQuota`。

**能保证**：上限的数量级和重置周期，而且来源可以自己点开核对（页面写着「每天 200 万」，解析结果就是 2,000,000/天）。

**不能保证**：

- **页面规则永远不会告诉你「你已经用了多少」**——那是个宣传页，不是你的账单；
- 页面改版、换措辞、变成前端渲染的 JS 页面，就抓不到（抓不到时保留旧值，绝不清空）；
- 旧值可能已经过时（官方悄悄把上限调低、或者免费模型直接没了），而规则层发现不了；
- 活动类描述（限时翻倍、新用户专享）识别不了，只会抓到第一个数字。

所以规则层只提供一个**上限**，需要账本配合才能算剩余；规则层单独用没有意义。

### 3. 实测探测（`probe`）

对候选 provider 发一次极小的真实请求：`max_tokens=1`、内容就一个 `1`。看返回：

- HTTP 429，或者错误信息里有 quota / 额度 / 限流 / 余额 / insufficient / exceed → `exhausted`
- HTTP 2xx → `ok`
- 网络不通、超时、5xx → `error`（**不算用完**，保留候选，宁可试一下也不误杀）

结果缓存 10 分钟写进 `data/quota-state.json`，同一次请求/同一段时间里不重复探——探测本身也花额度。

**能保证**：此时此刻，这个 provider 还能不能过一次真实请求。

**不能保证**：

- **不告诉你还剩多少**，只知道「能用/不能用」；
- 429 不一定是额度用完，也可能是并发/QPS 限流，探测分不清（只能按「用完」保守处理）；
- 只在这一瞬间有效。探测通过之后额度也可能被别处用光；
- 探测自己消耗一点 token，虽然就几个。

## 选路时怎么组合（`src/router.js`）

对 `candidates()` 排好序的候选，`quotaGate` 只处理 `tier: "free"`（或显式 `free: true`）的那些，`tier: "local"` 的本机模型不烧额度、也不探测：

1. 先用本地账本算 `remaining`，`left <= 0` → 跳过（`reason: local ledger 到上限`），不再浪费一次探测；
2. `left` 未知或还有剩 → `probe`，`exhausted` → 跳过（`reason: probe exhausted`）；
3. 免费档全被跳过 → 顺序里剩下的付费档接手（`fallback: true`，写 `data/route.log`）；
4. 连付费档都没有（没配、或者没填 key 算不 ready）→ 抛 `FREE_EXHAUSTED`：
   「免费额度都用完了，也没有可用的付费档：请配置一家付费模型，或等额度重置。」

两条兜底原则：

- 额度层自己出错（写文件失败之类）不跟着打死请求，写一条 `额度闸门异常，按候选继续` 的 `route.log`，按原候选继续；
- 探测 `error`（网络/超时/5xx）不当作额度用完。额度问题才跳过，网络问题交给后面的失败回退。

## 状态与日志

| 文件 | 内容 |
| --- | --- |
| `data/quota-state.json` | `probes`（每家的探测结果和时间）、`rules`（解析出的规则）、`updated_at` |
| `data/quota.log` | 每次 probe / refreshRules / 退付费，一行一条 JSONL |
| `data/route.log` | `额度跳过`、`免费额度用尽，退付费档`、`额度闸门异常` |

## 配置怎么写

`config.json` 里加公开页面来源（示例地址留空也行，不配就不刷新规则）：

```json
"quotaSources": [
  { "provider": "zhipu", "url": "https://open.bigmodel.cn/pricing" }
]
```

provider 上写免费上限：

```json
{
  "name": "zhipu",
  "tier": "free",
  "base": "https://open.bigmodel.cn/api/paas/v4/chat/completions",
  "model": "glm-4-flash",
  "key": "",
  "freeQuota": { "amount": 2000000, "unit": "token", "reset": "day" }
}
```

`amount` 是 token 数时 `unit` 写 `token` 或者不写。如果你想直接写「200 万」，就写 `{ "amount": 200, "unit": "wan", "reset": "day" }`——`remaining()` 会按 unit 换算。
`reset` 只有 `day` / `month` 两种，账本按本地日期（或年月）取数。
规则刷新回填的 `freeQuota` 一律是换算好的 token 数（`unit: "token"`），避免乘两次。

## 会误判的几种情况（诚实清单）

1. **多机 / 多客户端共用一个 key**：账本只算本机，`left` 偏乐观，可能先撞一次 429 才靠探测兜住。
2. **429 其实是并发限流**：会被判成 `exhausted`，10 分钟内这个免费档被跳过——方向是保守的（少花额度的代价是多花钱），但确实是误判。
3. **页面规则滞后或改版**：抓不到就保留旧值，旧上限可能早就变了。规则层兜不住，探测能兜住「还能不能用」，兜不住「还剩多少」。
4. **跨零点 / 跨月的重置时刻**：账本按本地时区切天，provider 按 UTC 或按账号自己的周期重置，重置前后几个小时的数字会有偏差。
5. **探测缓存 10 分钟**：这 10 分钟里额度刚被别处用光，我们不会立刻知道，会先失败一次再回退（失败回退本来就是兜底路径）。
6. **`max_tokens=1` 的请求被拒并不总是因为额度**：比如模型下线、参数变更也会报错，只要错误文本里出现 quota/限流/余额这些词，就会被保守判成用完。

结论：这套东西的作用是**把「明显没了」的免费档提前摘掉，并保证一定会退到付费档或者响亮地报错**，不是精确的余额表。要精确余额只有一条路——读你账号后台的账单，而我们不做那件事。

## 为什么不做「爬账号后台」

有更准的方案：登录账号后台，读真实余额。我们明确不做，理由不是难，是不该：

- **要凭据**。后台要看登录态，等于让一个开源脚本拿到你的账号密码/cookie/短信验证码。脚本被投毒、日志泄漏、仓库里误提交，代价都是你的账号。
- **要绕过风控**。后台页面大多带验证码、指纹、行为检测，「自动化读取」本质上就是绕过它们，违反服务条款，封号风险落你头上。
- **结构私有且易变**。这不是公开文档，改版就坏，还没法提前知道，坏了只能靠你去发现——维护成本全摊给每个用户。
- **和这个项目的定位冲突**。「clone 下来就能跑、不碰你账号」是前提，一旦开始存凭据，整个信任模型就变了。

而我们真正需要的只有两个问题：**「上限大概多少」和「现在还能不能用」**。前者公开页面上写着，后者一次 `max_tokens=1` 的探测就能回答，都不需要登录。剩下的差额（我到底用了多少）用本地账本估——估不准的部分，用「探测失败就退付费档」来兜底。

宁可保守地多花几分钱，也不拿你的账号去换一个更精确的数字。
