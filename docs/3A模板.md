# 3A 模板：调度 / 执行 / 质检

> 单A 是一个主脑单线程干到底；3A 把「干活的」和「验收的」拆开，验收不过就打回重做，
> 两次还不过就升级给人。两个模板**共用协议、不共用实现、数据不串**。

## 一、它长什么样

```
        ┌──────────────┐   信封    ┌──────────────┐   信封    ┌──────────────┐
 任务 → │ 调度 scheduler│ ───────▶ │ 执行 executor │ ◀─────── │ 质检 inspector│
        │ 唯一写状态的人 │ ◀─────── │ 调工具、干活   │ ───────▶ │ 按验收标准打分 │
        └──────┬───────┘   信封    └──────────────┘   信封    └──────┬───────┘
               │                                                    │
               │ 打回 ≤2 轮，超了升级                                 │
               ▼                                                    ▼
        ┌──────────────┐                                    ┌──────────────┐
        │ 状态落盘+日志 │                                    │ human（升级） │
        └──────────────┘                                    └──────────────┘
```

- **调度（`src-multi/scheduler.js`）**：拆任务、定验收标准、排依赖、发信封、收结果、
  决定「通过 / 打回 / 升级」。**整个 3A 里只有它能改任务状态**（单写者）。
- **执行（`src-multi/executor.js`）**：拿到提示词就干活——调模型、调工具、看返回值，
  交回「回复 + 用量 + 用了哪些工具」。它不给自己打分。
- **质检（`src-multi/inspector.js`）**：按验收标准逐条打分。判定用**和单A 同一把尺子**
  （`evals/lib/judge.js`），否则两边成绩没法比。不合格打回并带上失败理由，最多 2 轮，
  第 3 次不过就 `escalated` 升级给人。

代码目录（和单A 完全不互相 import）：

```
src-multi/
├─ protocol.js    信封 schema、角色、状态机、合法迁移
├─ scheduler.js   调度：单写者、落盘、恢复、打回/升级
├─ executor.js    执行：工具循环
├─ inspector.js   质检：按验收标准打分
├─ router.js      模型调用 + 账本（写 data-multi/ledger）
├─ memory.js      记忆（自己的实现：关键词召回/遗忘/事件/整理）
├─ tools.js       工具（文件/命令/记忆/提醒）
├─ safety.js      四级红线 + 审计
├─ sandbox.js     沙盒三档（none 默认 / process / docker）
├─ system.js      装配三个角色
└─ cli.js         命令行入口
evals-multi/
├─ run.js          同一份 tasks.json 跑 55 题 × 2 遍
└─ restart-test.js 调度重启恢复的真实验证
```

## 二、消息信封（强制 schema）

角色之间只认这一种 JSON，字段一个不能少：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 信封自己的 id |
| `from` | enum | `scheduler` / `executor` / `inspector` / `human` |
| `to` | enum | 同上 |
| `task_id` | string | 任务号 |
| `status` | enum | `planned` / `dispatched` / `completed` / `failed` / `rework` / `escalated` / `done` |
| `payload` | object | 载荷（执行结果、验收结论、打回理由…） |
| `ts` | ISO string | 发出时间 |
| `depends_on` | string[] | 依赖的任务号，可为空 |

写入前先过 `validateEnvelope()`：字段缺、角色非法、状态非法、`payload` 不是对象、
时间不可解析、`depends_on` 不是数组——**任何一条不合格就拒收**，写进
`data-multi/logs/rejected.log`，并在 journal 里记一笔。正常信封落
`data-multi/logs/envelopes.jsonl`，可逐条回放。

本轮 55 题 × 2 遍一共 560 个信封，拒收 0 个（说明收发两端都按 schema 来）。

## 三、状态机与单写者

```
pending → planned → running → inspecting → done
                         ↑          │
                         └─ rework ─┘        （最多 2 轮）
                                    └→ escalated（超 2 轮，升级给人）
任何阶段 → failed（执行重试 1 次仍失败 / 超时 / 前置依赖失败）
```

- 迁移只在 `scheduler.transition()` 里做，先过 `canTransition()` 再落盘；非法迁移直接抛错。
- 启动时抢 `data-multi/state/scheduler.lock`（写 pid）：已有活着的调度进程就**拒绝启动**，
  保证任何时刻只有一个写者。
- 每步落盘：`state/tasks.json`（当前状态）+ `state/journal.jsonl`（追加日志，只增不改）。

## 四、稳定性（对照 `docs/设计决定-两个模板.md` 的九条）

| # | 要求 | 3A 怎么做的 |
|---|---|---|
| 1 | 每步落盘、断点可续 | 状态文件 + journal，每次迁移即时写；进程重启后 `recover()` 接上 |
| 2 | 状态单写者 | 调度独占写；`scheduler.lock` 挡住第二个进程 |
| 3 | 超时三档分开 | 单次调用（router）、单任务执行（executor/scheduler `budget`）、整轮（budget） |
| 4 | 重试有上限（1 次）带退避、超了升级 | 执行失败重试 1 次（`running → planned`）；质检打回 2 轮后 `escalated` |
| 5 | 跨进程消息 schema 校验，不合格拒收并记日志 | `validateEnvelope()` + `rejected.log` |
| 6 | 幂等：同任务号重放不产生第二份副作用 | `submit()` 同 id 直接返回已有任务 |
| 7 | 启动自检 + 还原演练 | `--status` 看汇总；重启恢复有专门的 `restart-test.js` 真实演练 |
| 8 | 改动前先跑 Evals | 同一份 `evals/tasks.json`，同一把判定尺 |
| 9 | 所有动作留审计 | 工具调用写 `data-multi/audit.log`；状态迁移写 journal；信封写 JSONL |

### 重启恢复：真跑过，不是写在文档里

`node evals-multi/restart-test.js` 的流程：

1. 起 mock 模型（不要密钥），造 8 个可机器验收的小任务；
2. 起调度进程 A，跑完 2 个后 **SIGKILL 直接杀掉**（模拟崩溃）；
3. 检查落盘状态：2 个 done、1 个挂在 `running`、锁文件还在（进程已死）；
4. 用**同一条命令**起进程 B：它发现旧锁的 pid 已死 → 接管；把 `running` 判为「上次没收尾」，
   记一笔 recover 后重新排队；
5. 断言：8 个任务全部 `done`、每个任务只有一次 `done` 迁移、没有重复任务、
   journal 里确实有 recover、**单A 的 `data/` 一个字节没动**。

结果（每跑一次都会覆盖 `data-multi/restart-verify.json`）：

| 断言 | 结果 |
|---|---|
| 被杀前已有任务完成 | ✓（2 个）|
| 恢复后全部任务 done | ✓（8/8）|
| 每个任务只 done 一次 | ✓ |
| 确实触发了恢复（journal 有 recover） | ✓（1 条：r3 running）|
| 没有重复任务 | ✓ |
| 单A 数据没被碰 | ✓ |

## 五、数据目录（与单A 完全分开）

```
data-multi/
├─ state/tasks.json     任务状态（调度唯一写者）
├─ state/journal.jsonl  状态迁移/恢复/拒收 的追加日志
├─ state/scheduler.lock 单写者锁
├─ logs/envelopes.jsonl 角色间信封
├─ logs/rejected.log    被 schema 校验拒收的信封
├─ logs/route.log       模型失败切换日志
├─ audit.log            红线判定审计
├─ ledger/<日期>.json   按天账本
├─ memory/              记忆库与事件
├─ workspace/           工具工作目录
├─ results.json         55 题 × 2 遍的逐遍结果（字段与单A 对齐）
├─ report.md            报表（含「单A vs 3A」对照表）
├─ restart-verify.json  重启恢复验证记录
└─ .run/                评测时每题每遍的独立世界（可随时删）
```

评测时每一遍用 `data-multi/.run/<题号>/<遍>/` 做根目录，记忆/账本/审计/状态全在里面，
跑完就丢；不会污染 `data-multi/` 本体，更不会碰单A 的 `data/`。

## 六、怎么跑

```bash
# 一句话
node src-multi/cli.js "帮我记一下：我周三晚上打羽毛球"

# 批量任务
node src-multi/cli.js --jobs jobs.json --root data-multi

# 看状态（不干活）
node src-multi/cli.js --status

# 重启恢复演练（mock，不花钱，十几秒）
node evals-multi/restart-test.js

# 同一份 55 题跑两遍（本地 8B 约 40 分钟，可断点续跑）
node evals-multi/run.js --run
node evals-multi/run.js --report
```

## 七、这轮的成绩（同模型 ollama qwen3-8b-tool、同判定尺）

| 指标 | 单A | 3A |
|---|---|---|
| 两遍都过 | 54/55（98.2%）| 51/55（92.7%）|
| 单遍通过率 | 108/110（98.2%）| 106/110（96.4%）|
| 不稳定题 | 0 | 4 |
| 总耗时 | 2308.8s | 2562.7s（+11%）|
| 总 tokens | 237,910 | 248,924（+4.6%）|
| 云端折算成本 | 0.777146 元 | 0.824272 元 |
| 打回 / 升级 | 0 / 0 | 28 / 4 |

**结论要如实说**：这一轮 3A **没有**换来更高成功率，反而更慢更贵。原因在报告里有明细——
打回大多发生在「回复措辞没落在判定正则里」这种问题上，8B 被要求改时只是换个说法；
而真正的错误（读错文件、该拒没拒）单A 本来也过。

多角色不是免费的，也不是万能的。3A 的价值需要在**更复杂、多步骤、真会做错**的任务集上才看得出来；
这一轮的产出是：**同一把尺子下的可复现对比数据 + 一套真能重启续跑的骨架**，不是「3A 更厉害」的结论。

## 八、已知没做完 / 刻意没做

- **执行超时只做 Promise.race**：到点标记超时，但底层的模型请求不会立刻中止（Node 里拿不到取消句柄）。
- **恢复不保执行上下文**：重启后任务从「重新执行」开始，之前跑过的工具副作用会在同一工作目录里留着，
  但对话历史丢了；对幂等的任务是安全的，对「追加写文件」这类任务要小心。
- **没有 3A 的 HTTP 服务/页面**：这轮只做骨架 + 批量跑，入口是 CLI。
- **升级给人只是写日志 + 状态**，没有真正的通知渠道（邮件/IM 都没接）。
- **信封走本地文件**，不是消息队列；角色在同一进程内调用，靠文件留痕保证可回放。
- 沙盒默认 `none`；`docker` 可用性取决于机器，探测不到会明确回退 `process`。
