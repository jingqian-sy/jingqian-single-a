# 记忆设计：时间轴、事件层、遗忘曲线

这版记忆系统只做四件事，但每件都落到盘上：**存得下、搜得回、串成事、会变老**。

## 一、一条记忆长什么样

存 `data/memory/memories.json`，字段和 3A 模板共用同一套协议（实现各写各的，不互相 import）：

```
id            mem_xxxxx
text          一句话，尽量短（≤160 字以内最好）
kind          fact / preference / relation / emotional / lesson
importance    1~4，4 最重要
pinned        钉住就永不遗忘
created_at    创建时间
updated_at    最后修改时间
status        active / archived
```

雏版自用、不影响协议兼容的附加字段：`source`（谁写的）、`use_count`（被召回几次）、
`last_used_at`、`event_id`（归属哪个事件）、`vec`（向量缓存，可选）。

## 二、召回：两路并行，谁也别替谁

`src/memory/retrieve.js`

- **关键词一路**：中文按二元字组切、英文按词切，算 BM25（k1=1.2，b=0.75）。
  对专有名词、编号、人名准。
- **向量一路**：配了 `embedding.enabled` 才走，余弦相似度，阈值 0.3。
  对「意思相近但没共词」有用。没配 embedding 就自动降级成纯关键词，不报错、功能不残。
- **合并**：`0.55 × 关键词 + 0.45 × 向量`，再乘遗忘权重。
- **兜底**：钉住的记忆哪怕关键词一个都没命中，也给 0.22 的底分——
  免得「你答应过我什么」这种问题因为换了说法就召回不到。

## 三、遗忘曲线

不是按时间一刀切删，是**检索时降权**：

| importance | 半衰期 |
|---|---|
| 1 日常流水 | 14 天 |
| 2 一般 | 45 天 |
| 3 重要 | 120 天 |
| 4 钉住 | 365 天（pinned 直接不衰减） |

权重 = `0.5 ^ (距上次更新天数 / 半衰期)`，参与最终打分。所以老事不是没了，
是「不主动提，问起来还能翻到」。

## 四、事件层：零散一句话串成「一件事」

`src/memory/event.js`

- 按创建时间排序，**同一个实体 + 7 天窗口内**的记忆归成同一个事件；
- 实体从文本里抽（二元组 + 停用词过滤，最多 8 个）；
- 每个事件带：`event_id / title / start / end / entities / memory_ids / cause / result`；
- 检索时先给模型看事件时间轴（最近 5 件），再给具体句子——
  「按事件检索」而不是「按句子平铺」。

举个例子：周一「我买了个羽毛球拍」、周三「打球打得手酸」、周五「下周约了教练」——
三条会被串成一件「开始打羽毛球」的事，而不是三个孤立句子。

跑 `event_timeline` 工具或者 `GET /api/timeline` 能看到当前的事件串法。

## 五、主动整理：别让库无限膨胀

`src/memory/consolidate.js`，服务空闲时每 60 分钟自动跑一次
（`memory.idleConsolidateMinutes`，设 0 就关掉），也能手动 `POST /api/consolidate`。

三件事，全是规则驱动、不额外烧 token：

1. **合并重复**：字面相似度 > 0.85 且 kind 相同 → 留新的，归档旧的，重要性取高、pinned 继承；
2. **压摘要**：一件老事件（结束于 60 天前）里攒了 4 条以上、且没有 pinned 的，
   压成一条「（旧事摘要）……」，原文归档；
3. **重建事件层**：整理完把事件重新串一遍。

每次整理写一行 `data/consolidate.log`，能追溯谁被谁吃掉了。

## 六、写入从哪来

三条路：模型自己调 `remember` 工具、用户点明「记住/别忘/我喜欢」时的自动捕获、`POST /api/memory`。
自动捕获只认强信号正则（`src/core.js` 的 `CAPTURE`），不把每句闲聊都塞进库——
记忆库塞满流水账，召回质量反而崩。

## 七、跟 3A 的关系

协议一样（字段、事件、工具契约、红线级别），**实现不共用**。3A 那边有自己的库、
自己的账本、自己的评测；两个模板跑同一批任务才有可比性。
