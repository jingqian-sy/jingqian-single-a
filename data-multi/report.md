## 稳定性：调度重启恢复（真跑，不是口号）

- 怎么验的：调度进程 A 跑到一半被 SIGKILL 杀掉，再用同一条命令起进程 B 接管
- 被杀前：已完成 2 个，挂着的任务 r3
- 重启后：完成 8/8
- 恢复事件：r3(running)

| 断言 | 结果 |
|---|---|
| 被杀前已有任务完成 | ✓ |
| 恢复后全部任务 done | ✓ |
| 每个任务只 done 一次 | ✓ |
| 确实触发了恢复（journal 有 recover） | ✓ |
| 没有重复任务 | ✓ |
| 单A 数据没被碰 | ✓ |

> 明细：`data-multi/restart-verify.json`；日志：`data-multi/logs/restart-verify.log`。
> 恢复规则：进程启动时把 `running`/`inspecting` 的任务判为「上次没收尾」，记一笔 recover 后重新排队；
> 同一任务恢复超过 2 次判失败，不无限重试。

## 怎么复跑

```bash
node evals-multi/restart-test.js      # 先验重启恢复（mock，不花钱，十几秒）

node evals-multi/run.js --report      # 只重写这份报表
```

3A 的数据全在 `data-multi/`（记忆、账本、审计、状态、信封、报表），与单A 的 `data/` 完全分开。
